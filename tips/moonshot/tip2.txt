The README frames `humanlint` as an “open-source standard, paper, and audit CLI for agent-native engineering,” with a preferred profile of **Rust core + TypeScript/React/Vite + PostgreSQL + generated contracts + bounded Python**. # The moonshot

## Humanlint becomes the **Agent-Native Software Operating Standard**

Not “a linter.”

Not “another dev tool.”

Not “a style guide.”

**Humanlint becomes the default control plane for building software with agents.**

Its mission:

> **End vibe coding by making every repository self-describing, self-auditing, self-testing, self-securing, self-optimizing, and agent-operable from the first commit.**

The project should become the thing every serious team installs before writing code:

```bash
humanlint init
humanlint prove
humanlint repair
humanlint release
```

The goal is not to win a debate about languages. The goal is to make the old mess economically irrational. Humanlint should make substandard software feel like shipping without tests, shipping without auth, shipping without observability, shipping without a compiler, and shipping without brakes.

The existing standard is already pointed in this direction. Its own mission says the new standard should make wrong code easy to **reject, localize, prove, audit, and repair**, and that agents need enforceable paths rather than human-comfort-oriented conventions. ([GitHub][2])

# The name of the vision: **The Cold Star Standard**

A “cold star” is the fixed point every agent, developer, CEO, repo, CI system, and architecture decision orbits around.

It says:

> There is one highest-default way to build software: typed, bounded, observable, secure, measurable, contract-driven, rendered, tested, and repairable by agents.

This is how Humanlint “kills” bad software in practice: not by coercion, but by making every deviation visible, expensive, and temporary. Legacy stacks can exist, but they become migration targets. Exceptions can exist, but they expire. Alternative stacks can exist, but they must prove themselves against the same rubric.

The current standard already defines conformance levels **HL0 through HL5**, hard gates, stable rule IDs, ownership boundaries, generated zones, proof lanes, CI outputs, and finding schemas. That is the seed of a global standard. ([GitHub][3])

# Redefine “perfect code”

“Perfect code” cannot mean mystical code that never fails under unspecified requirements.

Humanlint should define perfect code as:

> **Code that is optimal against its declared specification, constraints, tests, threat model, performance budget, memory budget, UX contract, observability contract, and change policy.**

That makes perfection measurable.

A Humanlint-perfect repo has:

1. **A declared stack.**
2. **A declared architecture.**
3. **A declared owner map.**
4. **A declared contract map.**
5. **A declared proof map.**
6. **A declared UX proof map.**
7. **A declared security model.**
8. **A declared performance and memory budget.**
9. **A declared exception system.**
10. **A declared agent operating protocol.**

No hidden lore. No mystery folders. No “ask Dave.” No undocumented generated code. No random Python scripts under `tools/old2/final_final_really.py`. No UI that “passes tests” while visually breaking. No agent making broad edits because the repo did not tell it where the boundaries were.

The white paper’s core claim is already close to this: AI coding moves the bottleneck from “typing plausible code” to “getting trustworthy changes merged,” and Humanlint acts as a control plane for that merge trust. ([GitHub][4])

# The non-negotiable stack doctrine

The repo already names the target profile:

> **Rust core + TypeScript/React/Vite + PostgreSQL + generated contracts + bounded Python.** ([GitHub][1])

I would make that doctrine even sharper:

## Default stack

| Layer                |                                            Default | Why                                                                                                                                                                                                                                                   |
| -------------------- | -------------------------------------------------: | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Core/domain logic    |                                           **Rust** | Memory safety, concurrency discipline, high performance, strong compilation boundary. Rust’s ownership model is explicitly designed to catch memory and concurrency mistakes statically. ([Rust Documentation][5])                                    |
| Web UI               |                      **TypeScript + React + Vite** | Strict typing, componentized UI, fast dev loop, mature ecosystem. TypeScript strict mode strengthens correctness checks; Vite is built for fast frontend development; React is a component UI library. ([TypeScript][6])                              |
| Database             |                                     **PostgreSQL** | Constraints, foreign keys, transactional integrity, row-level security, mature query planning. PostgreSQL foreign keys and RLS policies are native tools for data integrity and access control. ([PostgreSQL][7])                                     |
| Contracts            | **Generated OpenAPI/Protobuf/JSON Schema clients** | No handwritten DTO drift. No “same shape in six files.”                                                                                                                                                                                               |
| AI/data escape hatch |                            **Bounded Python only** | Python allowed where it wins: ML, notebooks, data science, evaluation harnesses. It does not own product truth.                                                                                                                                       |
| Browser proof        |       **Playwright + Storybook + Humanlint UX QA** | Screenshots, traces, accessibility checks, deterministic geometry, visual baseline review. Playwright supports screenshots, visual comparisons, and trace debugging; Storybook supports visual testing and accessibility workflows. ([Playwright][8]) |

## But the doctrine must be empirical

Humanlint should not say “Rust because vibes.” It should say:

> Here is the rubric. Here is the score. Here is the measured tradeoff. Beat the default if you can.

The repo’s mission docs already define a 100-point stack rubric across correctness, security, performance, concurrency, boundaries, simplicity, ecosystem, observability, data integrity, and product velocity. ([GitHub][2])

That is the move: **make stack choice auditable**.

Java, PHP, Ruby, Go, Python, Kotlin, Scala, Swift, C#, or anything else should not be “banned by emotion.” They should be forced through the same scorecard. If they fail, they are migration targets. If they win in a domain, Humanlint can permit them through a versioned exception or domain pack.

## 2. `humanlint select`: stack and architecture selection

Before code exists, Humanlint should generate an architecture decision packet:

```bash
humanlint select --type b2b-saas --traffic 100k-rps --latency p95=80ms --compliance soc2 --ai-agent-heavy
```

Output:

```text
Recommended stack: rust-ts-vite-react-postgres-bounded-python
Architecture: modular monolith with explicit domain crates
Reason: lower agent confusion, lower memory risk, stronger generated contracts, simpler proof lanes
Rejected: Java/Spring, Python/FastAPI-only, Node-only
Migration risk: low
Proof lanes: fast, contract, db, web, e2e, security, perf, release
```

## 3. `humanlint prove`: evidence-driven development

Agents should not say, “I think I fixed it.”

They should say:

```json
{
  "claim": "checkout tax calculation fixed",
  "changed_paths": ["crates/domain/src/tax/*.rs"],
  "proof_lanes": ["fast", "contract", "property", "db"],
  "evidence": [
    "target/humanlint/evidence/unit.json",
    "target/humanlint/evidence/property.json",
    "target/humanlint/evidence/contract.json"
  ],
  "residual_risk": "none declared"
}
```

The repo already has the seed: proof lanes like fast, contracts, security, DB, UI, full, and audit are part of the mission docs. ([GitHub][2])

## 4. `humanlint qa`: deterministic rendered product proof

This is the answer to the CEO asking whether AI can replace human QA testers for pixels and layout.

The answer:

> Human QA should not disappear. Human QA should stop doing repetitive screenshot archaeology. Humanlint should use deterministic browser evidence to catch layout, accessibility, viewport, clipping, overflow, focus, target-size, and visual-regression failures before humans ever look.

The repo’s UX QA package is already excellent directionally: it combines Playwright screenshots, ARIA snapshots, viewport artifacts, deterministic geometry checks, visual baseline review, and review-only AI/VLM opinions unless backed by deterministic evidence. ([GitHub][1])

Moonshot Humanlint UX QA should cover:

* route screenshots,

* responsive breakpoints,
* ARIA snapshots,
* keyboard navigation,
* focus visibility,
* tap target size,
* text clipping,
* horizontal overflow,
* sticky obstruction,
* z-index misuse,
* button wrapping,
* form labels,
* contrast,
* layout shift,
* Lighthouse/Web Vitals,
* visual baselines,
* trace artifacts,
* design token drift,
* screenshot-to-issue localization.

## 5. `humanlint repair`: agent-ready fixes, not vague warnings

A finding should not be:

```text
Bad code found.
```

It should be:

```json
{
  "rule_id": "HLT-014",
  "severity": "high",
  "owner": "domain",
  "path": "crates/domain/src/billing/tax.rs",
  "problem": "duplicate tax calculation exists in two ownership zones",
  "why_it_matters": "agents may update one path and leave business truth divergent",
  "safe_fix": "move calculation into domain service and regenerate API contract",
  "proof_required": ["unit", "property", "contract"],
  "agent_prompt": "Refactor duplicate tax calculation into crates/domain/src/billing/tax_policy.rs without changing public API. Run just fast and just contract."
}
```

The standard already says findings should include severity, category, path, problem, agent fix, evidence, and version bindings. ([GitHub][2])

## 6. `humanlint migrate`: destroy legacy by making migration mechanical

This is the biggest commercial weapon.

Humanlint should be able to inspect a legacy app and produce:

* stack score,
* architecture map,
* domain extraction plan,
* DTO drift map,
* duplicate logic map,
* security gap map,
* test gap map,
* migration slices,
* risk-ranked rewrite plan,
* agent prompts,
* proof lanes for each slice.

Example:

```bash
humanlint migrate analyze ./legacy-java-service
humanlint migrate plan --target rust-ts-vite-react-postgres
humanlint migrate slice billing-tax
humanlint migrate prove billing-tax
```

The vision is not “rewrite everything blindly.” The vision is **measured strangler migration**:

1. Discover.
2. Score.
3. Extract contracts.
4. Generate test harness.
5. Port one domain slice.
6. Prove equivalence.
7. Cut over.
8. Retire old code.

## 7. `humanlint govern`: prevent entropy forever

Every standard dies if it becomes stale.

Humanlint should continuously ratchet:

* minimum score,
* allowed stack versions,
* deprecated patterns,
* security gates,
* performance budgets,
* UX rules,
* generated contract schemas,
* exception expirations,
* agent instruction compatibility.

A repo should not just pass once. It should stay alive.

# The Cold Star rubric

The current repo has two related score systems: mission-level stack scoring and repo audit scoring. I would unify them into one public rubric:

## Humanlint Cold Star Score: 100 points

| Dimension               | Weight | Meaning                                                                                  |
| ----------------------- | -----: | ---------------------------------------------------------------------------------------- |
| Correctness proof       |     12 | Unit, integration, property, contract, DB, and release proof.                            |
| Security                |     12 | SAST, secrets, vuln scans, dependency review, supply chain, threat model.                |
| Agent operability       |     12 | Owner maps, generated zones, agent docs, repair receipts, no contradictory instructions. |
| Contract integrity      |     10 | Generated clients, schemas, API drift detection, no handwritten DTO divergence.          |
| Architecture boundaries |     10 | Domain/application/adapters separation, dependency direction, no “utils soup.”           |
| Performance             |      8 | Benchmarks, latency budgets, bundle budgets, query budgets.                              |
| Memory efficiency       |      7 | Heap budgets, allocation checks, unsafe ledger, leak checks.                             |
| Concurrency safety      |      7 | Thread/task discipline, race tests, async boundaries, lock budgets.                      |
| UX proof                |      7 | Rendered browser evidence, accessibility, visual baselines, responsive states.           |
| Data integrity          |      6 | Migrations, constraints, RLS, backup/restore, seed validation.                           |
| Observability           |      5 | Traces, metrics, logs, correlation IDs, error catalog.                                   |
| Simplicity/minimality   |      4 | LOC caps, duplication control, dead-code control, no overengineering.                    |

Hard caps should remain brutal. A repo with no security lane, no root agent instructions, no generated-zone discipline, disabled tests, contract drift, silent fallbacks, direct DB misuse, or destructive migrations should be capped no matter how good the rest looks. The standard already defines hard gates around these kinds of failures. ([GitHub][3])

# The “no sprawl” principle

This is crucial.

The toolchain cannot become a giant mess of 90 dashboards and 200 npm packages.

Humanlint should install tools only under this law:

> **Every installed tool must feed one proof lane, emit one normalized evidence artifact, and map to one score dimension.**

No tool is allowed to exist because it is fashionable.

No tool is allowed to produce orphan output.

No tool is allowed to require a human to inspect five dashboards manually.

Everything writes to:

```text
.humanlint/evidence/
```

Everything is summarized into:

```text
repo-score.json
repo-score.md
humanlint.sarif
humanlint.release.json
```

* undocumented exceptions,
* contradictory agent instructions.

The mission docs already define vibe coding as plausible code that lacks ownership, proof, or repairability, and they list violations like duplicate logic, handwritten DTOs, silent fallbacks, mega files/functions, direct DB access, TODO-driven design, inconsistent naming, and conflicting instructions. ([GitHub][2])

# Roadmap

## Phase 0 — Current seed

Already present:

* Rust audit CLI.
* Agent standard.
* Owner map.
* Test map.
* Generated zones.
* Repo scoring.
* Paper.
* CI pattern.
* UX QA package.
* Playwright-based rendered artifacts.
* HL conformance concept.
* Rule IDs and hard gates.

The current repo map confirms the major pieces: `crates/humanlint`, `packages/ux-qa`, `agent`, `docs`, `paper`, `tips`, and `reference`. ([GitHub][1])

## Phase 1 — Make it installable as the default repo spine

Target:

```bash
cargo install humanlint
humanlint init
```

Deliver:

* `humanlint init`.
* Template generator.
* CI generator.
* Agent files generator.
* Proof lanes generator.
* Security lane generator.
* UX QA setup.
* SARIF output.
* GitHub Action.
* Standard lockfile.
* Exception registry.
* Version ratchet.

Success metric:

> A founder can run one command and get an agent-native repo with CI, QA, security, contracts, docs, and proof lanes.

## Phase 2 — Replace regex-heavy audit with semantic audit

The current scanner is a powerful start, but the next version should add AST and graph intelligence.

Deliver:

* Rust AST rules.
* TypeScript AST rules.
* SQL migration rules.
* Python containment rules.
* Dependency graph rules.
* Contract drift rules.
* Generated-code mutation rules.
* Semantic duplicate detection.
* Layer-boundary graph.
* Changed-path proof selection.

Success metric:

> Humanlint can tell not just that something looks wrong, but which architectural invariant it violates.

## Phase 3 — Build the reference product platform

Deliver:

```bash
humanlint init fullstack-saas
```

Creates:

* Rust API.
* Rust domain crates.
* PostgreSQL migrations.
* TypeScript React/Vite frontend.
* Generated API client.
* Storybook.
* Playwright.
* UX QA.
* Auth cell.
* Org/team cell.
* Audit-log cell.
* Observability.
* Security lanes.
* Release evidence.

Success metric:

> A serious SaaS product can start with Humanlint and not immediately rebuild the same boring infrastructure.

Deliver a registry:

```bash
humanlint cell search

```

Each cell has:

* contracts,

* tests,
* UX states,
* security policy,
* performance budgets,
* docs,
* repair recipes.

Success metric:

> Common software stops being rebuilt badly.

## Phase 5 — Migration engine

Deliver:


Support migration from:

* Java/Spring,

Success metric:

> Legacy stacks become measurable migration queues instead of permanent prisons.

Deliver:

* certified cells,
* rule-pack governance,
* reproducible audits,
* signed evidence,

Success metric:


Capabilities:

* duplication collapse,
* contract regeneration,
* dead code removal,
* performance tuning,
* memory optimization,
* UI regression repair,
* dependency cleanup,
* exception expiration.

Success metric:

> The repo improves itself faster than humans can manually maintain it.

# The killer feature: token minimization

Agent coding burns tokens because repos are ambiguous.

Humanlint should cut token waste by generating:

* `repo.intent.json`,
* `symbol-map.json`,
* `owner-map.json`,
* `test-map.json`,
* `contract-map.json`,
* `generated-map.json`,
* `route-map.json`,
* `error-map.json`,
* `proof-map.json`,
* `dependency-map.json`,
* `change-impact.json`.

Then an agent does not need to read the whole repo.

For any task:

```bash
humanlint context "fix checkout tax bug"
```

Output:

```json
{
  "read_first": [
    "crates/domain/src/billing/tax_policy.rs",
    "contracts/schemas/billing.schema.json",
    "tests/property/billing_tax.rs"
  ],
  "do_not_edit": [
    "contracts/generated/**",
    "apps/web/src/generated/**"
  ],
  "owner": "billing-domain",
  "proof_lanes": ["fast", "property", "contract"],
  "likely_rules": ["HLT-004", "HLT-009", "HLT-014"],
  "max_context_files": 7
}
```

This is how you stop agents from wandering.

# The governance model

Humanlint should become a living standard, not one person’s preference.

Create:

* Humanlint Foundation or standards group.
* Public rule registry.
* Public benchmark corpus.
* Versioned rule packs.
* Public conformance levels.
* Public certified templates.
* Public certified cells.
* Public migration reports.
* Public “bad pattern” museum.
* Public reproducibility harness.
* RFC process.
* Security advisory process.
* Deprecation calendar.

The standard must be opinionated enough to be useful and empirical enough to stay honest.

# The final vision statement

> **Humanlint is the Cold Star Standard for agent-native software: a universal, machine-verifiable control plane that turns every repo into a self-describing, self-testing, self-securing, self-optimizing system. It ends vibe coding by replacing guesswork with ownership, contracts, proof lanes, rendered UX evidence, security gates, performance budgets, and agent-readable repair receipts. It gives humans the thing they actually want: the ability to describe what should exist, while the machine enforces how it is built, proven, secured, optimized, and evolved.**

The highest ambition is not “better linting.”

The highest ambition is:

> **No more software chaos by default. No more agent drift by default. No more rebuilding the same broken foundations by default. No more unprovable code by default.**

Humanlint should become the first thing installed in every serious repo because it makes the alternative feel insane.
